# Technical Environment: `projen-terraform`

## Language and Package Manager

- **TypeScript** for the projen project-type definition (`.projenrc.ts` and the
  authored `TerraformProject` component) — same language as our CDK repos.
- **Node.js 22** (matches the CDK repos' Lambda/runtime baseline).
- **npm** as the package manager (the CDK repos use
  `javascript.NodePackageManager.NPM` — stay consistent).
- **Terraform / HCL** is the *generated* artifact language. Target **Terraform >= 1.6**
  (so native `terraform test` is available).

## Framework / Core Dependency

- **projen** (latest) — authored with `projen.Project` / the component model, not one
  of the built-in `awscdk.*` types. We are creating a NEW project type.
- Reference implementation to mirror: projen's `AwsCdkTypeScriptApp`, which already
  generates `build`/`upgrade`/`pull-request-lint` workflows, the self-mutation
  pattern, ESLint, Jest, and `tsconfig` from a single source.

## Terraform Tooling (the "ported learnings")

| Concern | CDK repo today | Terraform analog to generate |
| --- | --- | --- |
| Format | `eslint`/prettier | `terraform fmt -check -recursive` |
| Lint | ESLint (`eslintOptions`) | `tflint` with `.tflint.hcl` |
| Security scan | `cdk-nag` | `tfsec` and/or `checkov` |
| Validate | `tsc` typecheck | `terraform validate` |
| Docs | — | `terraform-docs` (inject between markers in README) |
| Tests | Jest | native `terraform test` and/or Terratest |
| CI trio | build/upgrade/pull-request-lint | identical trio, projen-generated |

## Cloud and Deployment

- The project type itself is **cloud-agnostic** — it generates a Terraform repo; the
  consuming team picks providers.
- Generated `versions.tf` scaffolds `required_providers` (default example: `aws`),
  but providers are user-configurable via projen options.
- No deployment performed by this tool; remote-state backend is scaffolded as config
  only (no provisioning) per the Vision's out-of-scope list.

## CI/CD

- **GitHub Actions**, generated by projen, must replicate the CDK repo's three
  workflows exactly in shape:
  - `build.yml`: `runs-on: ubuntu-latest`, `actions/checkout@v5`, install, run
    `npx projen build`, then the **self-mutation** detection job (diff → `repo.patch`
    artifact → second job applies & pushes via `PROJEN_GITHUB_TOKEN`).
  - `upgrade.yml`: `schedule: cron 0 0 * * *` + `workflow_dispatch`; runs
    `npx projen upgrade`; `peter-evans/create-pull-request@v7` opens the PR.
  - `pull-request-lint.yml`: `amannn/action-semantic-pull-request@v6`, types
    `feat`/`fix`/`chore`, `requireScope: false`.
- All three carry the projen "Generated by projen. To modify, edit .projenrc.ts" header.

## Testing

- **native `terraform test`** as the default (HCL `.tftest.hcl` files), wired into a
  projen `test` task and the `build` task.
- **Terratest (Go)** offered as an opt-in flag for teams that want programmatic tests.
- Jest is used only to test the project-type code itself (the synthesis logic),
  mirroring how the CDK repo unit-tests its stacks.

## Do NOT Use

| Prohibited | Reason | Use Instead |
| --- | --- | --- |
| CDKTF (`cdktf`, `cdktf-cli`) | We deliberately chose raw HCL, not TS-synthesized TF | projen-managed `.tf` files |
| Hand-edited `.github/workflows/*.yml` | Defeats the single-source-of-truth model; drift | Edit `.projenrc.ts`, run `npx projen` |
| Hand-edited `.tflint.hcl` / tfsec config | Same drift problem | projen-managed config files |
| `terragrunt` | Out of scope for MVP; adds orchestration layer | Plain Terraform + workspaces (Phase 3) |
| `pip`/`poetry` toolchains | This is a Node/TS + Terraform project | npm + Terraform CLI |
| Mutable workflow tokens / `GITHUB_TOKEN` for self-mutation push | Can't push back to PR branch reliably | `PROJEN_GITHUB_TOKEN` secret (as CDK repo does) |

## Security Basics

- Self-mutation push uses the `PROJEN_GITHUB_TOKEN` secret, never a plaintext token in code (matches CDK repo).
- Generated repos enforce `tfsec`/checkov on every PR as a **blocking** gate — security scanning is not opt-out in CI.
- `terraform validate` + `fmt -check` run before security scan so malformed HCL fails fast.
- No cloud credentials are embedded in the project type; scanning runs statically (no `terraform plan` against live accounts in MVP CI).
- Generated `.gitignore` excludes `.terraform/`, `*.tfstate*`, `*.tfvars` (secrets), and `crash.log`.

## Example Code Pattern

The authored project type should follow projen's component model, e.g.:

```typescript
import { Component, Project, YamlFile, github } from 'projen';

export interface TerraformProjectOptions {
  readonly terraformVersion?: string;   // default '>= 1.6'
  readonly providers?: Record<string, string>; // e.g. { aws: '~> 5.0' }
  readonly securityScanner?: 'tfsec' | 'checkov' | 'both';
  readonly enableTerratest?: boolean;
}

export class TerraformProject extends Project {
  constructor(options: TerraformProjectOptions = {}) {
    super({ name: options.name ?? 'terraform-app' });

    // Managed HCL (header-marked, regenerated on `npx projen`)
    new TextFile(this, 'versions.tf', { lines: renderVersionsTf(options) });

    // Managed tooling config
    new TextFile(this, '.tflint.hcl', { lines: renderTflint() });

    // projen tasks mirroring CDK's build pipeline
    const fmt = this.addTask('fmt', { exec: 'terraform fmt -recursive' });
    this.addTask('lint', { exec: 'tflint --recursive' });
    this.addTask('validate', { exec: 'terraform validate' });
    this.addTask('security', { exec: 'tfsec .' });
    this.addTask('docs', { exec: 'terraform-docs markdown table --output-file README.md .' });
    this.compileTask.spawn(fmt); // wire into build

    // The three GitHub Actions, generated (not hand-written)
    this.buildWorkflowWithSelfMutation();
    this.upgradeWorkflowNightlyPr();
    this.pullRequestLintSemantic();
  }
}
```

A generated `versions.tf` should look like:

```hcl
# ~~ Generated by projen. To modify, edit .projenrc.ts and run "npx projen".
terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}
```

A generated `build` GitHub Actions job should replicate the CDK repo's self-mutation
shape: run the build, `git diff --staged --patch --exit-code > repo.patch`, upload the
patch as an artifact, and have a dependent job apply it and push via
`PROJEN_GITHUB_TOKEN`.
