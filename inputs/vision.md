# Vision: `projen-terraform` — A projen Project Type for Terraform

## Executive Summary

`projen-terraform` is a reusable **projen project type** (in the spirit of projen's
`AwsCdkTypeScriptApp`) that lets a team spin up a fully-governed raw-HCL Terraform
repository with one command: `npx projen new --from projen-terraform`. Today, every
Terraform repo reinvents its own linting, security scanning, docs generation, and
CI/CD wiring by hand — and they drift apart over time. This project ports the
"batteries-included, single-source-of-truth" experience we already get from projen
on our CDK TypeScript repos to plain Terraform/HCL, so that formatting, linting,
security policy, docs, tests, and GitHub Actions are all generated and kept in sync
from one `.projenrc.ts` file.

## Problem Statement

We maintain multiple Terraform repositories alongside CDK repositories. The CDK repos
use projen, which means their ESLint config, Jest config, `tsconfig`, and the three
GitHub Actions workflows (`build`, `upgrade`, `pull-request-lint`) are all generated
and version-locked from a single `.projenrc.ts`. The Terraform repos have none of
this: `.tflint.hcl`, `tfsec`/checkov policy, `terraform fmt` enforcement,
`terraform-docs`, and CI workflows are all hand-authored, inconsistent across repos,
and drift whenever someone edits a workflow file directly. We want the same projen
governance model — managed files, self-mutation in CI, nightly dependency upgrades —
for Terraform, without forcing the team to learn CDKTF or rewrite infrastructure in
TypeScript.

## Target Users

| User type | What they need |
| --- | --- |
| Platform/DevOps engineers | Bootstrap a new compliant Terraform repo in seconds; never hand-write CI again |
| Terraform module authors | Auto-generated `terraform-docs`, lint, and test harness so modules ship documented and validated |
| Security / compliance reviewers | Guaranteed-present tfsec/checkov scanning and `terraform validate` on every PR, enforced not optional |
| Repo maintainers | Files regenerate from `.projenrc.ts`; CI self-mutates and fails on drift, exactly like the CDK repos |

## Key Success Metrics

- A new Terraform repo goes from zero to "lint + security + docs + CI passing" in under 5 minutes via `npx projen new`.
- 100% of generated workflow/lint/policy files are projen-managed (carry the "do not edit" header) — zero hand-edited governance files.
- The three GitHub Actions (`build` with self-mutation, `upgrade` nightly→PR, `pull-request-lint` semantic titles) behave identically to the CDK repo's versions.
- `terraform fmt -check`, `tflint`, `tfsec`/checkov, and `terraform validate` all run in CI and block merge on failure.
- `terraform-docs` output is regenerated by the `build` task and drift is caught by self-mutation.

## Features In Scope (MVP)

- A custom projen project type `TerraformProject` (TypeScript, authored with projen's component model) that others consume via `npx projen new --from <pkg>`.
- Managed root HCL files: `versions.tf` (required_version + required_providers), `main.tf`, `variables.tf`, `outputs.tf` scaffolds (created if absent, header-marked as managed where projen owns them).
- Managed tooling config: `.tflint.hcl`, tfsec/checkov config, `.terraform-docs.yml`, `terraform fmt` settings.
- projen tasks: `fmt`, `lint`, `validate`, `security`, `docs`, `test`, and a composite `build` task that runs them in order (mirrors `npx projen build` on CDK).
- The GitHub Actions trio, generated by projen, matching the CDK repo's behavior:
  - `build.yml` — runs `build`, detects self-mutation (e.g. regenerated docs/fmt), uploads+applies patch.
  - `upgrade.yml` — nightly; upgrades provider/tool pins; opens an auto-PR.
  - `pull-request-lint.yml` — semantic PR title validation (`feat`/`fix`/`chore`).
- A test harness option (native `terraform test` and/or Terratest) wired into the `test` task and CI.
- A README/docs scaffold and `terraform-docs` auto-injection between markers.

## Features Explicitly Out of Scope (MVP)

- CDKTF support — explicitly *not* this project; we chose raw HCL. (Possible Phase 2 alternate project type.)
- Publishing the project type to a public registry / multi-language JSII packaging (Phase 2).
- Terraform Cloud / Spacelift / Atlantis backend integration (Phase 2).
- Remote state backend provisioning (S3+DynamoDB lock table bootstrap) — scaffold config only, no provisioning (Phase 2).
- Multi-environment workspace orchestration / `terragrunt` (Phase 3).
- Policy-as-code beyond tfsec/checkov (OPA/Conftest, Sentinel) (Phase 3).
- Drift detection scheduling against live cloud state (Phase 3).

## Open Questions

- **Security scanner:** tfsec, checkov, or both? (tfsec is being folded into Trivy upstream — does that change the pick?)
- **Test framework:** native `terraform test` (HCL-based, 1.6+), Terratest (Go), or offer both as opt-in?
- **How much HCL does projen own?** Should projen *manage* `main.tf` content (header + regenerate), or only *scaffold it once* and then leave it user-owned? Managed files enable self-mutation/drift-catching but constrain the author.
- **Distribution:** is the project type consumed via `--from` a published npm package, or kept internal as a local `.projenrc.ts` external module? (We chose "reusable project type" — confirm npm publishing is in MVP or deferred.)
- **Provider version policy:** does `upgrade.yml` bump `required_providers` pins, the tool versions (tflint/tfsec/terraform), or both?
- **Node toolchain for an HCL repo:** projen requires Node to run. Is a Node dependency in an otherwise-Terraform repo acceptable to the team (it is for CDK repos)?
